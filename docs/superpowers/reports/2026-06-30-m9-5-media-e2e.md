## Repair Dispatch 修复

真实流程继续暴露了一个修复前工具语义 bug：Producer 调用 `dispatch_craftsman` 时传入：

```json
{
  "mode": "shot_video",
  "scope": {"type": "shot", "id": "shot_03"},
  "shot_refs": [],
  "force": true
}
```

预期只重做 `shot_03`，但工具结果显示“已将 3 个分镜视频 RenderPlan 任务加入队列”。根因是 `dispatch_craftsman.resolveShots` 只把 UUID 型 `scope.id` 视为单个 shot；当 `scope.id` 是 `shot_03` 这类 stable client key 时，`shot_refs=[]` 会退回“所有 active shots”。

已修复为：`scope.type=shot` 且 `scope.id` 非空时，优先按 UUID / semantic_key / client_key 解析单个 shot；只有 `scope.id` 和 `shot_refs` 都为空时，才允许默认派发全部 active shots。

回归测试：

```bash
cd apps/server
GOCACHE=/private/tmp/clipanvil-go-build go test ./internal/agent/tools -run 'DispatchCraftsman|SubmitReviewResult' -count=1
```

结果：PASS。新增测试覆盖 `scope: {"type":"shot","id":"shot_03"}` + `shot_refs: []`，断言只创建 1 个 Craftsman task。

修复前产生的 3 条仍会继续执行的 smoke 残留任务已在测试 workspace 标记失败，错误码为 `m9_5_smoke_cleanup_pre_fix_scope_expansion`，避免后续重启误执行。Producer 当前处于 `waiting_for_user`，这是 Reviewer rejected 后 repair 尝试仍未解决 shot_03 provider 拒绝时的合理 HITL 升级。
